## 必须修复的问题

### R1 同一兽 ID 可以改绑另一只实体

优先级：P1。位置：`Source/SummonerArchive.cs`，`BindFieldPawn` 第 394–434 行，尤其 423–426 行；关联 `BindRealmPawn` 与 `CheckConsistency`。

`BindFieldPawn` 只检查传入的新 Pawn 是否在界内或绑定其他兽，没有检查该兽记录是否已绑定另一只 Pawn，随后直接覆盖 `beast.pawn`。

路径：兽 A 已绑定界内 Pawn P1；给 A 调用 `BindFieldPawn(A, P2)`，其中 P2 是合法的地图/世界 Pawn。容量允许时，新绑定可以成功，但 A 的灵魂界条目仍持有 P1。结果是同一兽 ID 对应两个实体，记录指向 P2，而 P1 继续被深度保存。现有一致性检查对在场兽只检查容器是否持有它当前指向的 P2，未检查同 ID 条目中的 P1，因此也不能识别该分裂状态。

这是静态代码路径确认，真实 Pawn 的游戏内复现尚未执行。需拒绝替换不同实体，或通过明确的原子转移接口维持同一 Pawn；失败必须保持旧记录与容器不变。一致性检查须核对记录、容器与实体的双向对应关系。

### R2 修改容量或体量绕过上场上限

优先级：P2。位置：`Source/SummonerArchive.cs` 第 140–161 行、214–229 行。

`TrySetOccupySlots` 只检查值是否为 1 或 2，不验证修改后的在场占用。`TrySetCapacities` 检查了契约槽数量，却不检查现有在场占用是否超过新容量。

使用当前 DLL 的独立进程内存测试已复现：

| 操作 | 实际结果 | 应有结果 |
|---|---|---|
| 容量 1，兽占 1 且已在场，改体量为 2 | 返回 true；占用 2、容量 1；一致性报告超限 | 返回 false，保持原体量 |
| 兽在场占 2，容量由 2 降至 1 | 返回 true；占用 2、容量 1；一致性报告超限 | 返回 false，保持原容量 |

所有改变占用或容量的公开入口都应校验修改后的状态；失败要回滚或在写入前拒绝。不能只在进入在场状态时校验。

### R3 未决奖励不检查所属对象

优先级：P2。位置：`Source/SummonerArchive.cs` 第 522–544 行，尤其 531–543 行。

`AddPendingReward` 仅检查宿主召唤师存在和 `subjectId` 非空，不检查目标是否存在或归属该召唤师。当前 DLL 的内存测试中，召唤师 A 的兽可以被写入召唤师 B 的奖励队列。不存在的兽 ID 也不会因身份无效而被拒绝。

需按 `subjectKind` 验证目标身份：主人奖励指向当前主人记录，兽奖励指向存在且归属于当前主人的兽；一致性检查和加载后的验证也应识别失效或跨主人目标。失败不得增加队列或消耗 ID。

### R4 加载未完成仍报告存档测试通过

优先级：P2。位置：`Source/DataFoundationCheck.cs` 第 149–161 行。

`SaveAndLoad` 捕获栈中含 `DeepProfiler` 的空引用后，将 Scribe 强制设为 Inactive 并返回数据。上层仍可能报告 `SCRIBE PASS`。

本机游戏程序集的 `ScribeLoader.FinalizeLoading` 调用顺序为：`DeepProfiler.Start` → `ResolveAllCrossReferences` → `DoAllPostLoadInits`。在第一个调用处异常意味着后两阶段可能完全未运行。当前样例的主人和兽 Pawn 均为空，数值比对无法检出引用解析及加载后初始化缺失。

交付报告对这一限制的披露是准确的，但测试输出仍须调整：未完成加载只能标为部分字段读取通过、跳过或失败，不能归入完整存档往返 PASS。不能只检查 `Scribe.mode` 为 Inactive 就认为成功，因为失败路径也会设置该模式。
