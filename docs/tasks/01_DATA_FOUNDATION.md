## 需要实现的数据

| 对象 | 本轮范围 |
|---|---|
| 召唤师数据 | 唯一关联主人、熟练度、初始上场容量 1、初始契约位 1、契约槽列表、未决奖励列表 |
| 契约槽 | 稳定 ID、血脉标识、主兽身份、同血脉备用兽身份列表；主兽与最多 3 个备用兽分开计数 |
| 兽成长 | 稳定 ID、所属主人及契约槽、阶位 1–4、阶内等级 1–40、经验、普通属性投入记录、特殊变异记录、技能与工作记录 |
| 兽状态 | 是否在场/界内、休整状态、锁血冷却结束 tick、沉睡结束 tick、死亡标记；区分兽角色、位置和冷却，避免单枚举含义重叠 |
| 未决奖励 | 奖励所属对象、类型、来源阶位/等级、稳定 ID；为持久化候选项和选择状态预留明确结构，本轮不生成奖励或发放成长 |
| 灵魂界容器 | 建立持有真实 Pawn 的游戏级保存容器，明确谁拥有实体、谁仅引用；本轮不执行地图生成、撤回、复活或转移 |

采用符合 RimWorld 保存机制的 `GameComponent`、`ThingComp`、`IExposable` 等结构，自行选择最小合理组织方式。避免在游戏级记录与兽组件中各存一套可独立修改的同一数据；若需要缓存或索引，加载后重建并明确唯一数据来源。

读取当前安装的游戏程序集或本地接口确认实际 API。不要从需求文中的示例方法名推断 API 一定存在，不修改游戏原程序集。

## 保存和一致性要求

- 保存普通值、集合、稳定标识、主人与 Pawn 引用及冷却截止 tick；不得使用跨存档静态列表保存游戏状态。
- 对界内 Pawn 明确深度保存的所有权；在场 Pawn 使用引用，不得重复深度保存同一实体。加载后不得复制兽或丢失关联。
- ID 不依赖显示名称、集合位置或运行时对象哈希；保存后保持稳定。
- 空列表和首次加载有明确默认值；缺失字段可安全初始化，不要求兼容已经移除的旧版存档。
- 单只兽不得重复加入主兽/备用列表，也不得同时归属两个主人或两个契约槽。
- 容量校验区分契约数量与上场体量；不要因为备用兽存在就增加在场占用。
- 死亡档案保留身份和成长引用，供未来复活使用；真死时是否占槽、槽满如何复活，本轮不执行或硬编码。
- 为游戏内验收提供最小可复现方法，验证保存/读取后的身份、集合、未决奖励记录与冷却一致。可在独立测试环境使用开发工具或显式测试入口，不向正常玩家流程加入测试功能。

## 暂不确定的玩法规则

本轮仅保留所需字段与扩展点，以下问题写入交付说明，不自行补成正式规则：每阶 39/40 次奖励、多只同血脉兽同时上场、第二契约位解锁、经验速度、满级终局奖励、真死与复活占槽、主人死亡后处理。

不增加兽等级自动增长、技能学习、任务事件、实际锁血、沉睡治疗、复活、威胁点补丁或玩家 UI。不生成美术，不修改保留的贴图；后续美术由 Codex 提供。本轮不安装运行包到游戏目录、不操作玩家存档。

1. 运行 `Tools/Build.ps1` 和 `Tools/Verify-Package.ps1`，记录实际结果。
2. 验证上述数据一致性约束与保存往返。只有编译成功时，不得声称游戏保存/读取已经通过；若尚缺游戏测试环境，写明具体未验证项并给出复现步骤。
3. 检查未引入 VPE、VEF 或 Royalty 强制依赖，未恢复旧单狼玩法，未捆绑游戏或第三方程序集。
4. 在 `docs/tasks/01_DATA_FOUNDATION_RESULT.md` 写出完成内容、文件列表、数据所有权、保存方式、构建与测试证据、待决定规则和未完成事项。
5. 根据实际结果更新 `docs/STATUS.md`；完成本轮范围后停止扩展，等待下一轮任务。

交付供 Codex 从共享工作区审阅。不要伪造测试、把占位接口记为可玩功能，或为了本轮任务批量调整无关文档。
